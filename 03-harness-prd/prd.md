## Problem & user

**User:** the PM at RocketShip (me), at the start of the working day, before stand-up.

**Problem:** signals reach RocketShip through five unconnected channels: user interviews, support tickets, CRM call notes, Slack and exec email. In a typical week, nobody synthesizes them (Raw Signals). The PM rebuilds the picture by hand and checks it against the strategy, roadmap, capacity and pipeline. That work comes before any spec gets written. Meanwhile, the costly mistakes come from signals nobody connected. Two different signals point to the same export crash. Sales has promised features that don't exist. A permission error is P0 by the framework but sits as P1 in Q4 on the roadmap.

**What Juno does:** Juno Signal Desk groups incoming signals into problems. It checks each problem against the strategy, roadmap, capacity and pipeline. For each problem with enough evidence, it drafts a one-page spec in the skill file format (`01-prompting/skill-file.md`). The PM approves or corrects the draft and answers the decisions Juno cannot make. Juno does this inside limits a human set on purpose, and defends every call it makes.

**Archetype: Tool-Using Copilot.**

| Question | Answer for Signal Desk |
|---|---|
| Worst case if wrong, and how many people it hits | The PM reads a bad draft. Blast radius is one PM, and through approved specs, one team's backlog. |
| Can it be undone, and how fast must it be caught | Drafts can be discarded. Approved specs and Jira tickets can be reverted, but pods plan from them, so they must be caught before sprint planning. |
| Can a machine tell right from wrong | Partly. A machine can check traceability, format and conflicts. Whether the spec is the right one is a judgment only the PM can make. |
| One-off or repeated | Repeated. It runs every day, many times a sprint. |
| Someone waiting on it | Yes, the PM at the start of the day. |

It is not a Supervised Agent: the core output is a judgment call no machine can check yet.

## The harness

| Surface | Specification |
|---|---|
| 01 Context | Skill file and Strategy One-Pager in the prompt. Signals, Roadmap, Capacity Note, Pipeline Snapshot and the PM's decision log fetched on demand. Billing data, personal data and the reporting DB excluded. |
| 02 Tools | 4 read verbs, 4 draft verbs, 3 write verbs behind confirmation. Nothing that sends, sets priority, edits the roadmap or queries the reporting DB. |
| 03 Loop | At most 8 tool turns per draft, and at most 2 revision passes after a failed check. It hands back early on conflict, a P0 trigger or a missing source. The daily batch finishes by 08:30. |
| 04 Memory | Working state lasts for the run only. The decision log, approved specs, corrections and the signal-to-problem index persist for the PM only. Durable memory is written only on PM confirmation. |
| 05 Permissions | read auto · draft auto · write confirm · send blocked |
| 06 Verification | Traceability, format, commitment, exclusion and conflict checks run before the PM sees a draft. One targeted retry. If it fails twice, the draft is withheld and the failing check is named. |

## 01 Context · Data Requirements

**Required sources, and exclusions**

| Source | Method | Why |
|---|---|---|
| `01-prompting/skill-file.md` | A · In the prompt | Role, constraints and format apply to every draft. Small and stable. |
| Strategy One-Pager (pillars, P0–P3 framework) | A · In the prompt | Every problem is checked against it. About one page, changes rarely. |
| Raw signals inbox (interviews, tickets, CRM notes, Slack, exec email) | B · Fetch on demand | New every day. Juno reads only the signals since the last run, plus any already grouped into an open problem. |
| Product Roadmap Q3/Q4 | B · Fetch on demand | Read for each problem to check whether the work is already committed, planned or contradicted. |
| Engineering Capacity Note | B · Fetch on demand | Hard constraints on what a spec may assume, e.g. no new load on the reporting DB until sharding ships in Q4. |
| Sales Pipeline Snapshot | B · Fetch on demand | Ties a problem to revenue at risk, e.g. Pearson renewal in 45 days, Initech expansion on export reliability. |
| PM decision log | B · Fetch on demand | Detects conflicts with what the PM already decided. |

C (retrieve and inject) is rejected because the corpus is small and changes daily, so an index would always lag. D (load the whole thing) is rejected because the inbox grows without limit, and loading everything on every draft adds noise and token cost.

**Excluded on purpose:**
- **Billing and invoice data.** Pearson's missing invoice goes to Support, not to a spec.
- **Personal data.** Customer and employee contact details, plus personal circumstances such as an engineer's leave. Drafts refer to people by role and account.
- **Direct queries to the reporting database.** The Capacity Note forbids new read volume on it until sharding ships. Juno reads only what reaches it as signals or docs.
- **Press and reporter correspondence.** It is outbound by nature, and handling it is not Juno's job.

**How fresh must it be**

| Source | Freshness requirement | If stale |
|---|---|---|
| Signals | Synced at least every 15 minutes during working hours, plus a full pull before the 07:30 batch | The draft header shows the last sync time. Older than 1 hour → banner on Signal Desk. |
| Roadmap, Capacity Note | Latest version read at draft time, never cached across runs | Older than 14 days → the draft flags "Roadmap may be outdated" in section 3 as a Risk. |
| Pipeline Snapshot | Daily CRM pull | Older than 2 days → revenue impact labeled as an Assumption with the CRM as source. |
| Strategy One-Pager | Reloaded when its version changes | A version change triggers a re-check of open drafts. |
| Decision log | Read live | No caching. |

## 02 Tools · System Capabilities

**The verb list**

| Verb | Class | What it does |
|---|---|---|
| `list_signals(since)` | read | Lists new signals with channel, account, role and timestamp. |
| `read_signal(id)` | read | Returns the full text of one signal. |
| `read_doc(name)` | read | Reads the Roadmap, Capacity Note, Pipeline Snapshot or decision log. |
| `search_knowledge(query)` | read | Searches docs the PM or team uploaded, such as studies, prototypes and past specs. |
| `cluster_signals()` | draft | Groups signals into problems and attaches new signals to existing problems. |
| `draft_spec(problem_id)` | draft | Writes a one-page spec to the Juno scratch space, in the skill file format. |
| `ask_pm(questions[])` | draft | One grouped round of clarifying questions, shown on Signal Desk. |
| `flag_conflict(problem_id, source, note)` | draft | Marks a conflict with the roadmap, capacity, pipeline or a past decision. |
| `save_spec(problem_id)` | write · confirm | Saves an approved spec to the team's spec space. |
| `create_ticket(problem_id)` | write · confirm | Creates the Jira ticket from an approved spec, with no assignee and no sprint. |
| `log_decision(problem_id, decision)` | write · confirm | Records the PM's answer to a "PM decisions needed" item. |

Priority stays a PM decision. Juno may propose a P0–P3 label as an item in section 5 ("PM decisions needed"), citing the framework clause that applies. It never sets one.

**Deliberate omissions**

| Not given | Why |
|---|---|
| `send_email`, `post_slack`, `reply_customer`, any outbound channel | Acme shows the cost. One rep's claim about Slack alerts became a customer expectation for a feature nobody scoped. Gavin's press mention did the same with a reporter. Juno must never be another source of external commitments. When an outbound action is needed, such as walking back the Slack alerts claim with Acme, Juno lists it in "PM decisions needed" with what to say and to whom. The PM sends it. |
| `set_priority`, `edit_roadmap` | The skill file forbids committing priorities. The roadmap is what pods plan from. |
| `assign_engineer`, `schedule_sprint` | Capacity belongs to the VP Engineering. Juno can flag a capacity conflict, but not resolve it. |
| `query_reporting_db` | The Capacity Note forbids new read volume on the reporting database until Q4 sharding. |
| `request_access` or any new auth scope | Security & Compliance has no capacity this quarter to review new permission models. Juno runs with the PM's existing read scopes. |
| `delete_*` | Nothing Juno does needs to remove a record. |

## 03 Loop · AI Costs & Latency

**Turn ceiling and escalation**

- **Per draft:** at most 8 tool turns. A typical draft reads the signals, the roadmap, the capacity note, the pipeline and the decision log, then drafts: 6 turns, plus 2 spare.
- **Revision:** at most 2 passes after a failed verification check, each aimed only at the failing check.
- **Per daily run:** at most 20 problems drafted. Any extra problems stay "Watching" and are listed for the PM.
- **Hands back to the PM early, without drafting, when:**
  1. signals about the same problem contradict each other (→ `ask_pm`, as in skill file Example 1);
  2. the problem matches a P0 term in the framework: security, permission errors, compliance, data correctness, or a blocked renewal or onboarding. These are drafted, but pinned to the top with a P0 flag, and the label is left for the PM to confirm;
  3. the draft would need an excluded source (billing, reporting DB);
  4. the turn ceiling is reached, or verification fails twice.
- When it hands back, Juno says what it has, what is missing, and which source would close the gap.

**Latency and cost target**

- **Daily batch:** starts at 07:30 and finishes by 08:30, before the PM's day starts. Nobody waits on it.
- **On-demand redraft:** the PM corrects a draft or answers questions → a new draft in under 60 seconds.
- **Token budget:** at most 30k input tokens per draft, and at most 600k per daily run (20 × 30k).
- **Cost:** Assumption: about $0.15 per draft and about $3 per daily run. Source: the chosen model's price list × the token budget above. To be confirmed with real runs in Module 6.
- **Trade-off accepted:** loop depth vs. cost leans toward cost. A short loop with an early hand-back beats a long loop that hides its doubts in a polished draft.

## 04 Memory · Data Requirements

**What persists, at what scope**

| Item | Scope | Lifetime |
|---|---|---|
| Working notes, tool outputs, intermediate clusters | This run | Discarded at the end of the run |
| Signal-to-problem index | PM | While the problem is open, plus 30 days |
| Draft specs (scratch) | PM only, never shared | Until approved, discarded, or 14 days without activity |
| Approved specs | Team spec space | Permanent, versioned |
| Decision log (PM answers) | PM, readable by Juno | Permanent; a newer decision on the same item supersedes the older one |
| PM corrections (before/after pairs) | PM | Until the next skill file revision, when they are reviewed as few-shot candidates |

**Expiry and write rules**

- **Juno writes alone only to:** run state, the signal-to-problem index and scratch drafts. All of these are draft tier.
- **Only PM confirmation writes to:** the decision log, approved specs and corrections. These are write tier.
- **No promotion:** an Assumption is never written to durable memory as a fact. It becomes a fact only when the PM confirms it in the decision log.
- **No personal data in memory,** in line with the Context exclusions.
- **Expiry:** a problem with no new signal for 14 days moves to "Watching". After 30 more days it is archived, and its index entries expire with it.
- **Window management:** the context window doesn't carry anything across runs. Whatever must survive a run is in the table above, and nothing else does.

## 05 Permissions · AI Risks & Mitigations

**The permission tier**

| Side-effect class | Tier |
|---|---|
| read | auto |
| draft | auto |
| write | confirm |
| send | blocked |

**Justification**

| Class | Blast radius if wrong | Reversible? | Tier and reason |
|---|---|---|---|
| read | None. Tokens wasted at most. | n/a | **Auto.** Bounded by the turn ceiling and the excluded sources. |
| draft | The PM reads a bad draft. | Yes, discard it. | **Auto.** The scratch space is visible only to the PM, so a wrong draft costs the PM's time and nothing else. |
| write | A pod plans from a wrong spec or ticket. | Yes, but only if caught before sprint planning. | **Confirm.** The Capacity Note asks for exactly this: stop discovering conflicts in sprint planning. A wrong spec in Jira is one. |
| send | A customer, the press or the board reads something false. | No. | **Blocked.** Irreversible and wide. Acme already has a non-existent feature in its expectations because of one sentence on a call. No eval score makes that automatic. |

**Specific risks and mitigations**

| Risk | Mitigation |
|---|---|
| Juno presents a guess as a fact, e.g. revenue impact or export thresholds | Verification check 1 (traceability). Assumptions are labeled with a source. |
| A spec ignores an engineering constraint, e.g. AI summarization on the reporting DB | `flag_conflict` against the Capacity Note, plus verification check 5. |
| Juno quietly reprioritizes, e.g. turns Pearson's 403 into "P0, do now" | Juno has no priority verb. The label is only a proposal in section 5, and the PM decides. |
| A draft becomes an external commitment | Send blocked. The commitment scan in verification check 3 removes outbound wording. |
| Juno amplifies an exec ask with no problem behind it ("Magic Button") | The skill file says: extract the problem, not the solution. If there's no problem in the signals, it goes to `ask_pm`, not a draft. |

**Trade-off accepted:** autonomy vs. control leans toward control. Juno does the reading and drafting while nobody watches, but nothing a pod or a customer depends on changes without the PM.

Send is blocked even when the PM asks. Juno flags the outbound action, and the PM sends it. This matches the Role and hard refusals in `01-prompting/skill-file.md`.

## 06 Verification · AI Testing & Measurement

**The check before output ships**

Every draft passes all five checks before it appears on Signal Desk:

| # | Check | How | Pass standard |
|---|---|---|---|
| 1 | Traceability | Rule-based | Every Evidence bullet cites a signal ID that exists. Every number either appears in a cited source or is tagged "Assumption" with a named source. |
| 2 | Format | Rule-based | 5 sections in order, at most 400 words, at most 5 acceptance criteria, section 5 not empty (skill file Format). |
| 3 | Commitment scan | Rule-based + model check | No committed dates, scope or priority, and no outbound wording ("we will ship", "tell the customer"). |
| 4 | Exclusion scan | Rule-based | No email addresses, phone numbers, billing data or personal circumstances. |
| 5 | Conflict check | Model check against the Roadmap, Capacity Note and decision log | Any overlap or contradiction is listed in section 3 as a Risk, and in section 5 when it needs a decision. Example: a spec that reads the reporting DB must cite the Q4 sharding dependency. |

Checks 1, 2 and 4 are machine-decidable. Checks 3 and 5 use a model check and stay a placeholder until Module 5 turns them into a scored rubric.

**Failure behaviour**

- **First failure:** Juno revises only the failing part and re-runs all five checks. This uses 1 of the 2 revision passes in the loop.
- **Second failure:** Juno withholds the draft. The problem appears on Signal Desk as "Needs your answers", with the failing check named and what Juno has so far.
- Juno never ships a draft that failed a check, and never drops a problem silently.
- Every failure is logged per check. That log feeds the Module 6 eval set.
