# Agent Control Panel · Juno

_Module 4 deliverable. Generated by `M4 - Agent Control Panel.html`. Paste over `04-agentic-workflows/agent-control-panel.md`._

## What Juno Is Doing

**Pillar:** spec drafting, through Juno Signal Desk (`02-prototype`). It runs inside the harness in `03-harness-prd/prd.md`, and neither the skill file nor the harness changes. What changes is who starts it. Until now, the PM triggered each draft. From now on, a daily batch starts at 07:30 without the PM. It groups the overnight signals into problems and drafts one-page specs, so they are waiting when the PM sits down.

**Level: 2 · Semi-Autonomous (Human-in-the-Loop).**
- **Not level 1:** the value is having drafts ready before the day starts. A tool the PM has to trigger loses that.
- **Not level 3:** whether a spec is the right one is a judgment call no machine can check yet. Every action that changes what a pod plans from (write), or what a customer hears (send), needs a person.
- This is the lowest level that does the job.

**Reasoning pattern:** one ReAct loop per problem (think, act, observe, until the 5 checks pass), started by a fixed batch script rather than a planner agent. The list of problems comes from one clustering step at the start of the run. There is no handoff between agents, so there is no step that can drop between a planner and an executor.

**Failure mode watched most closely: silent failure.**
- Each draft depends on 5 sources (signals, Roadmap, Capacity Note, Pipeline Snapshot, decision log). If one read fails quietly, Juno produces a confident draft that breaks a real constraint. For example, it might propose AI summarization on the reporting DB because the Capacity Note never loaded.
- **Second watch: reasoning drift.** Juno could start from a signal's suggested solution and end up specifying it, as with Gavin's "Magic Button" or Acme's TikTok ask, instead of the problem behind it.

## Four Levers

**Stop Conditions** (Loop):

The loop for one problem ends at the first of these:

| # | Condition | Result |
|---|---|---|
| 1 | **Done:** the draft passes all 5 verification checks from the PRD | Draft posted to Signal Desk as "Draft ready" |
| 2 | 8 tool turns used | Hand back (see Fallback Protocols) |
| 3 | 2 revision passes failed verification | Draft withheld |
| 4 | Same tool called with the same arguments twice in one loop | Stop that problem as a loop. Never try a third time. |
| 5 | 90 seconds of elapsed time on one problem | Hand back |
| 6 | A required source returns anything other than `ok` after 1 retry | Stop, no draft |

The whole daily run ends at the first of these: 20 problems processed, a budget of 600k input tokens, or 08:30.

_Guards against:_ infinite loops (4), the latency tax (2, 5 and the run cap), and silent failure (6).

**Structured Tool Outputs** (Tools):

Every tool returns the same envelope. Juno never has to interpret free text to know whether a call worked.

```json
{
  "tool": "read_doc",
  "status": "ok | empty | partial | error",
  "source": "capacity_note",
  "as_of": "2026-10-24T07:31:02Z",
  "items": [ { "id": "CAP-PLAT-2", "text": "No new read/write volume on reporting DB until sharding ships." } ],
  "error": { "code": "TIMEOUT", "message": "…", "retryable": true }
}
```

- `status` is required. `empty` and `partial` are never treated as `ok`.
- Each item carries a stable `id`. A signal is `SIG-<channel>-<n>`, for example `SIG-SLACK-5`, and a doc clause is `CAP-…`, `RMAP-…`, `PIPE-…`, `DEC-…`. Draft Evidence and Risks cite these IDs, which is what verification check 1 tests.
- `as_of` is required. It is compared with the PRD freshness rules, for example the Roadmap is stale after 14 days.
- Write verbs (`save_spec`, `create_ticket`, `log_decision`) return `pending_confirmation` until the PM confirms. Only then do they return `ok`, with the record ID.
- Each run ends with a run report: `signals_in`, `signals_assigned`, `signals_unassigned`, `drafted`, `asked`, `blocked`, `watching`, `not_reached`. `signals_in` must equal `signals_assigned + signals_unassigned`. If it doesn't, the report is flagged on Signal Desk.

_Guards against:_ silent failure. A failed read can't pass as an empty result, and a signal can't disappear between ingestion and the board.

**Confidence Thresholds** (Verification):

Juno stops and asks when any of these is true, and checks them before every `draft_spec` call and before posting:

| Condition | Juno does |
|---|---|
| Fewer than 2 signals support the problem, or they come from only 1 source | No draft. Marked "Watching". (Dark mode, the bright nav bar.) |
| Signals on the same problem contradict each other | One grouped round of `ask_pm` and no draft (skill file Example 1) |
| A signal names a solution, and none of the signals states a problem it solves | No draft. Asks the PM what problem it is meant to solve. (Gavin's "Magic Button", TikTok for Acme.) |
| An Evidence claim has no signal ID, or a number appears in no source | Remove the claim or label it "Assumption" with a source. If more than 2 Assumptions are needed in sections 1–2, ask instead of drafting. |
| A required source is `empty`, `partial`, `error` or stale | No draft. Names the missing source. |
| The problem hits a P0 term in the framework (security, permission error, compliance, data correctness, a blocked renewal or onboarding) | Draft, but pinned to the top with a P0 label to confirm. "Approve" stays locked until the PM confirms or changes the label. (Pearson 403, CSV export.) |
| The draft conflicts with the Roadmap, Capacity Note or a past decision | Draft, with the conflict as a Risk in section 3 and an item in section 5 (Pearson 403 is P0 by the framework but P1 in Q4 on the roadmap). |
| The next step is a write or an outbound action | Always stop for the PM (see Checkpoints) |

_Guards against:_ silent failure, because missing evidence becomes a question instead of a guess, and reasoning drift, because a solution never becomes a spec without a problem behind it.

**North Star** (Context):

> Turn today's signals into one-page spec drafts the PM can approve or correct, with every claim traced to a signal, nothing decided and nothing sent.

- This sentence is restated at the top of every turn, together with the **pinned problem statement**: the one-sentence problem Juno extracted in the first step of each loop, which is then fixed.
- Before `draft_spec`, and before each revision, Juno compares the draft's Problem section with the pinned statement.
- If they no longer match, for example the pinned statement is "CSV export fails on large files" and the draft now specifies "AI-generated reports", Juno stops that problem and flags it as drifted. It never rewrites the pinned statement to fit the draft.

_Guards against:_ reasoning drift.

## Rules of Engagement

**Agency Permission:**

| Juno decides alone (read, draft) | Juno proposes and waits (write) | Never (send, and anything not in the verb list) |
|---|---|---|
| Which signals belong to the same problem | Save an approved spec (`save_spec`) | Email, Slack or any message to customers, sales, press or execs |
| Whether a problem gets drafted, asked about or watched | Create a Jira ticket, without assignee or sprint (`create_ticket`) | Set or change a priority, edit the roadmap |
| The wording of the draft and of the questions | Record a PM answer (`log_decision`) | Assign engineers, plan sprints |
| Flagging conflicts and suggesting a P0–P3 label as a PM decision | | Query the reporting DB, request new access, delete anything |
| Listing an outbound action the PM should take, with what to say and to whom | | Edit its own skill file |

**Access Control:**

- **Identity:** Juno runs with the PM's existing read scopes only. It never requests new auth scopes, because Security & Compliance has no capacity this quarter to review a new permission model.
- **Can read:** the signal inbox (email, Teams, Slack, support tickets, CRM call notes), the Roadmap, the Capacity Note, the Pipeline Snapshot, the Strategy One-Pager, Knowledge docs the PM or team uploaded, and the decision log.
- **Cannot reach:** the reporting database, billing and invoices, HR and personal data, and press correspondence.
- **Can write alone:** its scratch space (visible to the PM only) and the signal-to-problem index.
- **Can write after PM confirmation:** the team spec space, Jira (create only) and the decision log.
- **Memory by type:**

| Type | What | Who writes |
|---|---|---|
| Working | This run's context and tool outputs. Cleared at the end of the run. | Juno |
| Episodic | Signal-to-problem index, run reports, failure log per check | Juno |
| Semantic | Strategy, approved specs, decision log | PM, or Juno after PM confirmation |
| Procedural | `01-prompting/skill-file.md` | PM only. Juno can propose a few-shot from the PM's corrections but can't apply it, so a bad correction can't compound on its own. |

**Fallback Protocols:**

Each stop condition has its outcome decided in advance. Every outcome ends in a visible state on Signal Desk, never in a skipped problem.

| Trigger | Fallback |
|---|---|
| Required source not `ok` | 1 retry after 60s if `retryable`. If it is still not `ok`: "Blocked: <source> unavailable", no draft, and the source is named in the run summary. |
| 8 tool turns or 90 seconds reached | Hand back as "Needs your answers", with what Juno has, what is missing, and which source would close the gap |
| Verification failed twice | Draft withheld. The failing check is named, and the partial draft stays visible in Raw signals for context. |
| Loop detected (same call twice) | That problem stops, it is logged in the failure log, and the run moves on to the next one |
| Drift detected (North Star mismatch) | That problem stops as "Drifted". The pinned statement and the drifted draft are shown side by side for the PM. |
| Run cap reached (20 problems, 600k tokens or 08:30) | Remaining problems marked "Not reached today", carried over to the next run and counted in the run summary |
| Signal ingestion down | Banner with the last successful sync. Juno drafts only from what arrived and says so in each draft's header. |
| Run report doesn't reconcile | Banner on Signal Desk listing the unaccounted signal IDs |

The board opens with a one-line run summary, for example: "Run 07:30–08:04 · 4 drafted · 2 need your answers · 1 blocked (Capacity Note) · 3 watching · 0 not reached".

**Checkpoints:**

1. **Morning review (every draft).** Nothing leaves the scratch space until the PM opens it. Approve stays locked until every item in "PM decisions needed" is answered.
2. **Before every write.** `save_spec`, `create_ticket` and `log_decision` show exactly what will be written, and they run only on PM confirmation.
3. **P0 label.** Any problem flagged P0 needs the PM to confirm or change the label before approval.
4. **Outbound actions.** Juno lists them, for example "Walk back the 'real-time Slack alerts' claim with Acme before signing: Sales rep, before contract". The PM sends them. No step that reaches outside the org runs through Juno.
5. **Weekly.** The PM reviews the failure log and the correction log. Only the PM promotes a correction into the skill file's few-shot examples.
